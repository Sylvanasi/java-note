# 09｜空闲检测与心跳保活

## 1. 为什么要检测空闲

建立了 TCP 连接，不代表应用始终能及时知道对方是否仍可正常工作。也可能只是双方暂时没有业务消息。

应用可以约定一个时间范围：多久没有读到期望数据就触发检查，多久没有业务发送就主动发送心跳。

空闲说明一段时间没有相应读写，不直接证明对方宕机。关闭、继续观察或发探测消息，属于应用策略。

## 2. IdleStateHandler 三个参数

```java
new IdleStateHandler(readerIdleSeconds,
                     writerIdleSeconds,
                     allIdleSeconds)
```

这个三个整数参数的构造方法单位是秒，0 表示关闭对应检测。

| 参数 | 条件 | 对应事件状态 |
|---|---|---|
| readerIdleSeconds | 连续指定时间没有读到数据 | READER_IDLE |
| writerIdleSeconds | 连续指定时间没有写出数据 | WRITER_IDLE |
| allIdleSeconds | 连续指定时间既没读也没写 | ALL_IDLE |

读空闲不因单纯写数据而消失；写空闲不因单纯读数据而消失。全部空闲则要求这段时间两个方向都无相应活动。

## 3. 是入站还是出站

IdleStateHandler 是双向 Handler，观察读写活动。产生的 IdleStateEvent 沿入站事件方向传播，由后面的 userEventTriggered 接收。

它本身不会因为配置了读空闲就自动关闭连接，要在回调中明确决定。

## 4. 服务端读空闲检测

```java
ch.pipeline()
  .addLast(new IdleStateHandler(20, 0, 0))
  .addLast(new LengthFieldBasedFrameDecoder(1024, 0, 4, 0, 4))
  .addLast(new ChatMessageDecoder());
```

放在分帧器前时，观察的是经过该节点的原始读取活动；收到不完整片段也可能更新读活动，并不专门统计完整业务消息。

后续 Handler：

```java
@Override
public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
    if (evt instanceof IdleStateEvent event
            && event.state() == IdleState.READER_IDLE) {
        System.out.println("连续 20 秒未收到数据，关闭连接");
        ctx.close();
        return;
    }
    ctx.fireUserEventTriggered(evt);
}
```

日志应与真实配置一致。时间阈值是实验/应用约定，不是 Netty 固定要求。

## 5. 客户端写空闲时发 PING

```java
.addLast(new IdleStateHandler(0, 10, 0))
```

```java
@Override
public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
    if (evt instanceof IdleStateEvent event
            && event.state() == IdleState.WRITER_IDLE) {
        ctx.writeAndFlush(new Models.ChatMessage((byte) 2, "PING"));
        return;
    }
    ctx.fireUserEventTriggered(evt);
}
```

PING 是经过现有 ChatMessageEncoder 编码的普通应用消息，不是 TCP 内部控制报文。

## 6. 服务端识别并回复

```java
if (msg.type() == 2) {
    ctx.writeAndFlush("PONG\n");
    return;
}
```

本实验回复方向是换行文本，所以 PONG 带换行；它只回复发送方，不加入业务群发。

## 7. 心跳流程

```text
客户端暂时没有业务写出
    ↓ 达到写空闲阈值
发送 type=2 的 PING
    ↓
服务端读到数据，读空闲计时更新
    ↓
回复 PONG
    ↓
客户端按行读取文本回复
```

有正常业务数据持续写出时，写空闲可能不触发，因此无需仅为了保活重复发送同样频率的心跳。

## 8. 阈值的关系

检测允许的无数据时间应给心跳间隔留出余量，考虑调度延迟和网络抖动。当前实验是服务端读空闲 20 秒、客户端写空闲 10 秒；较早也用过 6 秒与 2 秒。

定时器不是硬实时。EventLoop 或业务执行器被占住，也可能推迟事件处理。

当前客户端只设置写空闲，没有单独实现“等待 PONG 的截止时间”。因此目前完成的是 PING/PONG 与服务端空闲清理，不应描述成已经具备完整的双端故障判定和自动重连。

## 9. 正常关闭与超时

正常关闭时通常能很快收到 TCP 的结束通知并关闭 Channel，不必等到空闲阈值。

如果只是静默掉线、迟迟没有收到结束通知，才可能由应用空闲策略补充处理。

测试空闲时，用 nc 建立连接后不输入可以观察服务端超时；但向长度协议的端口随意输入普通文本，会先触发协议错误。
