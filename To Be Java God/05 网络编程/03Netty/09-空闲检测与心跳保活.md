# 09｜空闲检测与心跳保活

![[附件/知识总览/09-空闲检测与心跳保活.svg]]

## 1. 空闲是观测结果，不是死亡证明

TCP 已建立，不代表应用总能及时知道对端是否仍能正常工作；没有业务消息也可能只是正常安静。应用通过空闲阈值触发检查，再决定发探测、继续观察还是关闭。

空闲检测、应用 PING/PONG、TCP keepalive 与业务 ACK 处于不同层次。收到 PONG 可用于判断对应探测得到回应，但不能证明任意业务已经持久化；仅有空闲事件也不能证明对端宕机。

## 2. 三类空闲条件与事件方向

```java
new IdleStateHandler(readerIdleSeconds,
                     writerIdleSeconds,
                     allIdleSeconds)
```

这个三个整数参数的构造方法使用秒，0 关闭对应检测；带 TimeUnit 的其他构造方法则按指定单位。

| 检测 | 条件 | 事件 |
|---|---|---|
| 读空闲 | 指定时段内没有相应读取活动 | READER_IDLE |
| 写空闲 | 指定时段内没有相应写活动 | WRITER_IDLE |
| 全空闲 | 指定时段内读写都没有相应活动 | ALL_IDLE |

单纯写不能消除读空闲，单纯读不能消除写空闲。这里的活动是处理器所观察的 I/O 活动，不是对端业务成功证明；调用 write 也不能直接等同于对端已收到。

IdleStateHandler 是双向 Handler，观察读写，产生的 IdleStateEvent 通过入站用户事件向后传播，由后续 userEventTriggered 处理。它本身不因为读空闲就自动关闭连接。应用消费事件后可停止传播，其他事件则应按需要继续 fire。

## 3. 放置位置决定观察粒度

```java
ch.pipeline()
  .addLast(new IdleStateHandler(20, 0, 0))
  .addLast(new LengthFieldBasedFrameDecoder(1024, 0, 4, 0, 4))
  .addLast(new ChatMessageDecoder());
```

放在分帧器前，读空闲观察原始输入活动，不完整片段也可能更新读活动。它不专门统计完整合法业务消息。因此持续传少量片段，并不能仅靠此阈值判断一条完整消息是否在合理时间内完成。

放在分帧或业务解码后，会观察不同粒度的输入；出站还必须确保写操作实际经过该节点。不要只移动 Handler 位置，却仍按原来的统计语义解释事件。

当前服务端实际配置读空闲 20 秒，后续 ChatHandler 在 READER_IDLE 时调用 ctx.close。源码日志仍写“连续 6 秒未收到数据”，与配置不一致；实际阈值应以配置为准，本次只整理知识，不修改项目代码。

```java
@Override
public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
    if (evt instanceof IdleStateEvent event
            && event.state() == IdleState.READER_IDLE) {
        ctx.close();
        return;
    }
    ctx.fireUserEventTriggered(evt);
}
```

## 4. PING 与 PONG 的实际路径

客户端当前配置写空闲 10 秒：

```java
new IdleStateHandler(0, 10, 0)
```

```java
if (evt instanceof IdleStateEvent event
        && event.state() == IdleState.WRITER_IDLE) {
    ctx.writeAndFlush(new Models.ChatMessage((byte) 2, "PING"));
    return;
}
```

PING 使用现有 ChatMessageEncoder，线上仍为长度、类型和 UTF-8 正文；不是 TCP 控制报文。服务端收到相关字节会更新对应读活动，完整解码后识别 type=2，并只给发送方回复：

```java
if (msg.type() == 2) {
    ctx.writeAndFlush("PONG\n");
    return;
}
```

回复方向为换行文本，客户端由按行分帧器和 StringDecoder 接收。PING 不进入业务群发。服务端读活动的更新发生在字节被前置 IdleStateHandler 观察时，不必等业务 Handler 已处理或 PONG 已发送。

有正常业务写活动时，写空闲可能不触发，这种设计可以减少空闲期间之外的额外心跳。当前客户端还每 12 秒定时发业务消息，这与写空闲触发发送是两种任务，不应混为固定 12 秒心跳。

## 5. 阈值余量与当前可靠性边界

服务端允许无数据时间应给客户端探测间隔留余量，并考虑网络抖动、任务排队、EventLoop 阻塞与业务执行器延迟。当前配置为服务端 20 秒读空闲、客户端 10 秒写空闲；这些是实验参数，不是 Netty 或 TCP 固定要求。

定时器不是硬实时；探测消息也可能因写缓冲或业务拥塞延迟。收到空闲事件时应按应用容忍度处理，不能只根据一个阈值承诺准确识别全部故障。

当前客户端只是写空闲发 PING、打印收到的文本，没有实现 PONG 截止时间、探测关联、重连与会话恢复。因此具备的是 PING/PONG 流程及服务端空闲清理，不是完整的双端故障判定和恢复方案。

## 6. 正常关闭与验证场景

正常远端结束常能通过 TCP 的结束或后续 I/O 信号及时发现，默认常见配置下可关闭连接，不必先等空闲阈值。半关闭等配置需另行区分；静默断网、网络黑洞没有及时带来结束信号时，超时机制才提供补充检测。

| 场景 | 应观察什么 |
|---|---|
| nc 建立连接后不输入 | 服务端读空闲事件与关闭，阈值按实际配置解释 |
| 正常客户端长时间无业务 | 写空闲产生 PING，服务端回复 PONG |
| 持续正常业务发送 | 是否无需额外空闲心跳也能更新活动 |
| 服务端不回复 PONG | 当前客户端缺少回应超时判定，不能宣称会自动重连 |
| 正常主动关闭 | 关闭事件无需先等待心跳超时 |

向长度协议端口随意输入普通文本，可能先触发协议错误，不能把这种断开当作空闲超时。上述表格是验证目标；本次做了源码核对，没有重新运行网络与故障实验，不能标记实测通过。
