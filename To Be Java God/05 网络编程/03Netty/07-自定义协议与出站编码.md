# 07｜自定义协议与出站编码

## 1. 为什么对象需要编码

网络传输的是字节流。Java 对象不能直接作为对象跨过网络，双方要约定字段怎样变成字节、怎样识别边界、怎样还原。

```text
ChatMessage 对象
    ↓ 出站编码器
ByteBuf 中的连续字节
    ↓ Netty 写出与本机 TCP
网络传输
```

手写字段编码不要求对象实现 Serializable；它与 ObjectOutputStream 的 Java 序列化协议是不同方式。

## 2. 本实验消息对象

```java
public class Models {
    public record ChatMessage(byte type, String content) {}
}
```

- type=1：业务消息。
- type=2：应用层 PING。
- content：UTF-8 正文。

类型数值由应用协议约定，不是 TCP 的 SYN、ACK、FIN 等标记。

## 3. 线上字节格式

```text
┌─────────────────┬─────────────┬──────────────────┐
│ 长度 N：4 字节   │ 类型：1 字节 │ UTF-8 正文字节    │
└─────────────────┴─────────────┴──────────────────┘
```

本协议定义：

```text
N = 1 + 正文 UTF-8 字节数
整帧字节数 = 4 + N
```

长度字段自身的 4 字节不计入 N。这个规则是双方约定的，不是所有协议都如此。

## 4. hello 为什么写入长度 6

hello 本身只有 5 字节；N 还包括类型的 1 字节，所以是 6。

```text
type=1，content=hello

00 00 00 06 | 01 | 68 65 6c 6c 6f
──────────   ──   ──────────────
整数6        类型1 正文hello
占4字节      占1字节 占5字节
```

整条消息是 10 字节。`writeInt(6)` 表示用固定 4 字节存整数 6，不是写 6 个字节，也不是写字符 '6'。

## 5. 出站编码器

```java
public class ChatMessageEncoder
        extends MessageToByteEncoder<Models.ChatMessage> {

    @Override
    protected void encode(ChannelHandlerContext ctx,
                          Models.ChatMessage msg,
                          ByteBuf out) {
        byte[] bytes = msg.content().getBytes(StandardCharsets.UTF_8);
        out.writeInt(Byte.BYTES + bytes.length);
        out.writeByte(msg.type());
        out.writeBytes(bytes);
    }
}
```

`out` 是 Netty 为编码准备的输出缓冲区。这里按协议顺序追加字节，框架再把输出传给后续出站步骤。

正常使用这个编码器时，不要在 encode 中自行释放 out，也不需要自己在末尾 fireChannelRead。

## 6. writeByte 与 writeBytes

```java
out.writeByte(msg.type()); // 一个 byte
out.writeBytes(bytes);    // 一组字节
```

`msg.type()` 是基本类型 byte，没有 `.length`。类型字段固定 1 字节，可以用 `Byte.BYTES` 让表达更明确。

## 7. 字符数不等于字节数

```java
String content = "你好";
byte[] bytes = content.getBytes(StandardCharsets.UTF_8);
```

这里正文占 6 字节，N=7，整帧=11 字节。计算网络长度要用编码后的 bytes.length，不用 content.length()。

## 8. 三次 write 是否发送三次

不是。编码器中的三次 write 是向同一个 ByteBuf 连续追加数据：

```text
writeInt → out 中有长度字段
writeByte → out 后面追加类型
writeBytes → out 后面追加正文
```

完成后是一个连续字节序列。实际 Socket 写入、TCP 分段与接收方 read 的次数不与这三行代码一一对应。

## 9. 两方向可以使用不同协议

本实验保留：

```text
请求：长度 + 类型 + 正文
回复：UTF-8 文本 + 换行
```

因此服务端请求方向使用长度字段分帧和对象解码；客户端回复方向仍使用按行分帧和 StringDecoder。每个方向的发送端与接收端必须配套。
