# 07｜自定义协议与出站编码

![[附件/知识总览/07-自定义协议与出站编码.svg]]

## 1. 对象与应用协议

TCP 提供字节流，Java 对象需要按双方约定转换成字节，再由接收方解析。应用协议至少要约定消息边界、字段类型、字符编码和长度含义。

```java
public class Models {
    public record ChatMessage(byte type, String content) {}
}
```

笔记示例中，type=1 表示业务消息，type=2 表示应用层 PING，content 使用 UTF-8。它们是应用约定，不是 TCP 的 SYN、ACK、FIN 标记。

手写字段编码不要求实现 Serializable；它与 ObjectOutputStream 使用的 Java 序列化格式是不同方案。

## 2. 帧结构与长度含义

| 在线顺序 | 字段 | 固定大小或含义 |
|---|---|---|
| 1 | 长度 N | 4 字节整数，当前 writeInt 使用大端序 |
| 2 | 类型 | 1 字节 |
| 3 | 正文 | UTF-8 编码后的字节序列 |

本协议定义 `N = 1 + 正文 UTF-8 字节数`，`整帧大小 = 4 + N`。N 包含类型，不包含长度字段自身的 4 字节；它不是“正文长度”或“整帧长度”。

双方必须采用同样的字节序与计数规则。其他协议可以采用不同约定，不能把此处的 N 公式当作统一标准。

## 3. 用字节数计算，不能用字符数

| 正文 | UTF-8 正文字节数 | N：类型加正文 | 整帧字节数 |
|---|---:|---:|---:|
| hello | 5 | 6 | 10 |
| 你好 | 6 | 7 | 11 |
| 空字符串 | 0 | 1 | 5 |

例如 type=1、content=hello 的十六进制字段为：

| 长度字段 | 类型 | 正文 |
|---|---|---|
| 00 00 00 06 | 01 | 68 65 6c 6c 6f |

writeInt(6) 使用固定 4 字节保存整数 6，不是写入 6 个字节，也不是写字符 '6'。

String.length 表示 UTF-16 代码单元数量，不能代替编码后的字节数。必须先按指定字符集生成 bytes，再用 bytes.length 计算。空字符串与 null 也不同；下面的局部编码示例假定 content 非 null。

## 4. MessageToByteEncoder 的职责

```java
public class ChatMessageEncoder
        extends MessageToByteEncoder<Models.ChatMessage> {
    @Override
    protected void encode(ChannelHandlerContext ctx,
                          Models.ChatMessage msg,
                          ByteBuf out) {
        byte[] bytes = msg.content().getBytes(StandardCharsets.UTF_8);
        out.writeInt(Byte.BYTES + bytes.length);
        out.writeByte(msg.type());
        out.writeBytes(bytes);
    }
}
```

out 是框架为编码准备的输出缓冲区。writeInt 追加长度，writeByte 追加类型，writeBytes 追加正文；msg.type 是一个基本类型 byte，没有 length。

MessageToByteEncoder 处理匹配的消息类型；不匹配的消息通常继续向前面的出站处理器传递。因此，装上这个编码器不意味着任意对象都会变成 ChatMessage 协议。

正常 encode 方法只按格式填充 out，不自行释放 out，不调用 fireChannelRead，也不在其中再次 write 相同输出造成重复发送。框架负责后续出站交接。

若业务从自己的 ctx 发起写操作，编码器必须位于该 Context 可到达的出站路径上。协议要求的字段合法性和最大消息大小也需明确，不能认为编码成功就代表接收方一定接受。

## 5. 缓冲区写入与网络发送的区别

编码器内三次 ByteBuf 写方法是向同一个输出缓冲区连续追加字节，不是三次 Socket 发送，也不对应三个 TCP 报文。

编码结束、出站 write、flush、Socket 写入、TCP 分段和对端读取，属于不同层次。对端可能一次收到多帧，也可能多次才读齐一帧；必须由接收端按协议恢复消息边界。

因此，看到 writeInt、writeByte、writeBytes 三行代码，不能推断三次抓包或三次 channelRead。出站操作成功也不能替代接收方业务确认。

## 6. 两个方向分别配套

本次核对的 chat-socket-lab 源码中，两方向使用不同格式：

| 方向 | 发送格式 | 接收端处理 |
|---|---|---|
| 客户端请求服务端 | 长度 N + 类型 + UTF-8 正文 | LengthFieldBasedFrameDecoder 分帧，再由 ChatMessageDecoder 解码 |
| 服务端回复客户端 | UTF-8 文本，以换行划分消息 | LineBasedFrameDecoder 分帧，再由 StringDecoder 转成字符串 |

客户端请求由 ChatMessageEncoder 编码；服务端回复使用 StringEncoder，换行需由应用内容提供。StringEncoder 只做字符编码，不自动补换行。

客户端请求正文里即使含换行，也不改变请求按长度分帧的规则。双向通信不要求两方向协议相同，但每个方向的发送端与接收端必须配套。

这里的源码核对只确认当前格式和处理器配置；不表示异常输入、边界长度或网络故障已通过运行验证。
