# 10｜连接管理与群发

![[附件/知识总览/10-连接管理与群发.svg]]

## 1. ChannelGroup 管理连接集合

ChannelGroup 是线程安全的 Channel 集合，支持对集合中的目标批量 write、flush、close。DefaultChannelGroup 会在加入的 Channel 关闭后将其移除，一个 Channel 也可以加入多个组。

| 对象 | 组织什么 |
|---|---|
| EventLoopGroup | 事件循环及其执行资源 |
| ChannelGroup | Channel 集合及批量操作 |
| ChannelPipeline | 一个 Channel 的处理步骤 |

加入组不会改变连接所属的 EventLoop，也不会使多个连接共享 Pipeline。集合线程安全不代表其中的业务状态或任意消息对象天然线程安全。

## 2. 在线集合的共享与生命周期

```java
private static final ChannelGroup online =
        new DefaultChannelGroup(GlobalEventExecutor.INSTANCE);
```

当前服务端在每条连接初始化时创建 ChatHandler，static 字段让这些实例共享一个进程内的在线集合。若每个 Handler 都新建一个独立集合，它就不能自然表示全部连接。也可由服务对象持有并注入共享集合，不是只有 static 才能做到共享。

构造器执行器用于组结果等通知，实际连接 I/O 仍由各自 EventLoop 执行。这个集合不跨进程共享，也不是已经认证的用户列表；用户身份、房间成员与连接的映射仍需应用定义。

```java
@Override
public void channelActive(ChannelHandlerContext ctx) {
    online.add(ctx.channel());
    ctx.fireChannelActive();
}
```

加入的是接受客户端连接得到的 Channel。监听端口不是群聊接收者，不应把监听 Channel 当普通用户加入业务广播集合。

DefaultChannelGroup 根据 Channel 关闭自动移除；本场景不必在 channelInactive 再做同样的 remove。但自动移除不负责清理应用另行维护的用户 Map、房间、缓存或排队资源。手工 remove 只移出集合，本身也不等于关闭 Channel。

## 3. 单发、广播与心跳分流

| 调用 | 目标 |
|---|---|
| ctx.writeAndFlush(text) | 当前 Context 所属连接的出站路径 |
| online.writeAndFlush(text) | 组中本次操作覆盖的目标连接 |

本例集合中都是普通连接，广播默认包含发送方。若需要排除发送方、按房间发送或定向私聊，应显式选择目标，不是 ChannelGroup 自动理解业务身份。

```java
@Override
protected void channelRead0(ChannelHandlerContext ctx,
                            Models.ChatMessage msg) {
    if (msg.type() == 2) {
        ctx.writeAndFlush("PONG\n");
        return;
    }
    online.writeAndFlush(
            ctx.channel().remoteAddress() + "：" + msg.content() + "\n");
}
```

PING 只回给当前连接，业务消息只提交一次群发。若同一处理路径残留两次 online.writeAndFlush，会产生两次应用发送，不能简单归因于 TCP 重传。

当前源码的业务分支实际上对所有非 type=2 消息群发，并未显式只接受 type=1；不能把示例描述为已经具备完整消息类型校验。

## 4. ChannelGroupFuture 与失败目标

```java
ChannelGroupFuture groupFuture = online.writeAndFlush(text);
groupFuture.addListener(f -> {
    if (!f.isSuccess()) {
        for (ChannelFuture target : groupFuture) {
            if (!target.isSuccess()) {
                System.out.println(target.channel().remoteAddress()
                        + " 写失败：" + target.cause());
            }
        }
    }
});
```

单连接操作返回 ChannelFuture；组操作返回由各目标结果组成的 ChannelGroupFuture。可以检查全部成功、部分失败，并遍历或按 Channel 查找单个结果。它表示这一次组操作的目标结果，不是对未来所有入组连接的长期承诺。

**失败目标不一定是发送者。** 原消息处理方法中的 ctx 指向发送方，群发某个目标写失败时直接 ctx.close，关掉的可能是健康的发送者。是否关闭失败目标，要结合具体失败和策略决定。

组写成功也只代表相应本地写操作成功，不证明所有接收方都已完成业务。业务可靠投递仍需消息 ID、ACK 等应用机制；不要在 I/O 回调中阻塞等待组结果。

## 5. 同一个客户端程序建立多条连接

启动同一个 NettyClient main 的两个进程，就有两条独立连接。它们连接相同服务端端口 9094，本地端口在未指定时通常由操作系统分配；无需复制 NettyClient2，也无需更改服务端目标端口。

IDE 允许时可开启同一配置的多实例运行；不同版本入口可能不同，也可从两个终端分别启动。

验证广播应发送 type=1 业务消息，而不是仅发送 PING。应观察 A 发消息时 A、B 都能收到，B 发消息时双方也能收到，再检查 B 关闭后集合不再保留 B。这里列出验收方法，本次没有重新启动客户端或运行故障实验。

## 6. 换行、重复输出与验证边界

当前回复方向使用换行分帧。请求正文若已包含末尾换行，服务端再拼接换行，客户端可能读到额外空行；它不一定代表业务逻辑执行了两次。

| 现象 | 优先检查 |
|---|---|
| 两端都收到自己的消息 | 广播是否按设计包含发送方 |
| 业务内容出现两份 | 是否两次提交群发、重复触发业务或重复连接 |
| 多一个空行 | 正文与服务端追加的换行是否叠加 |
| 某目标失败后发送者断开 | 失败处理是否误用了发送者 ctx |
| 连接关闭后仍有其他状态 | 自动移组之外的用户映射、队列等是否清理 |

当前 ChatHandler 源码已核对：业务群发只调用一次，组回调目前只打印全部成功，未逐目标处理失败。笔记中的失败遍历是局部示例，不表示项目已实现或验证该分支。
