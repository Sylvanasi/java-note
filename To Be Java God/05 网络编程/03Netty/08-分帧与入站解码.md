# 08｜分帧与入站解码

![[附件/知识总览/08-分帧与入站解码.svg]]

## 1. 分帧确定范围，解码读取字段

分帧从字节流中提取完整消息的字节范围，输出通常仍为 ByteBuf；业务解码再读取类型、正文并生成 ChatMessage。编码端写出一个 ByteBuf，不保证接收端一次 read 就得到完整消息。

以长度 N=6、类型为 1、正文 hello 为例：先收到长度、类型与 he 时，尚缺 llo 的 3 字节，分帧器先保留，不向后输出半帧。如果长度字段的 4 字节都未收齐，也需要先等待；一次输入含多帧时则逐条提取。

## 2. 长度字段分帧器的五个参数

```java
new LengthFieldBasedFrameDecoder(1024, 0, 4, 0, 4)
```

| 参数 | 值 | 本协议中的作用 |
|---|---:|---|
| maxFrameLength | 1024 | 整帧上限，包含长度字段；不是正文上限 |
| lengthFieldOffset | 0 | 长度字段从帧起点开始 |
| lengthFieldLength | 4 | 长度字段占 4 字节 |
| lengthAdjustment | 0 | N 已包含类型和正文，不再额外加类型长度 |
| initialBytesToStrip | 4 | 输出前跳过最前面的 4 字节 |

通用计算关系为：`整帧长度 = 长度值 + lengthAdjustment + 长度字段末尾偏移`。末尾偏移是 lengthFieldOffset + lengthFieldLength；本例得到 `整帧 = N + 4`。

本协议 N=1+正文字节数，所以 1024 字节整帧上限对应最大 1019 字节正文。超长帧会按分帧器规则报 TooLongFrameException；应用仍需定义异常处理策略，不等于框架一定按业务预期断开连接。

## 3. 去掉长度字段后输出什么

| strip 参数 | 向下游输出 |
|---|---|
| 4 | 类型与完整正文 |
| 0 | 长度字段、类型与完整正文 |

strip 控制输出时跳过多少字节，不改变前面计算整帧长度时的计数规则。不能把“去掉长度字段”理解为长度字段从未参与分帧。

当前源码使用 strip=4，下游业务解码器不再读取长度字段。分帧器不负责把 type=1、type=2 解释为业务或 PING，也不自动生成 ChatMessage。

## 4. ByteToMessageDecoder 的解析与输出

以下局部实现与当前 ChatMessageDecoder 的核心逻辑一致，前提是前置分帧器已输出一帧的类型与正文：

```java
@Override
protected void decode(ChannelHandlerContext ctx,
                      ByteBuf in,
                      List<Object> out) {
    if (!in.isReadable()) {
        throw new CorruptedFrameException("消息缺少类型字段");
    }
    byte type = in.readByte();
    byte[] content = new byte[in.readableBytes()];
    in.readBytes(content);
    String text = new String(content, StandardCharsets.UTF_8);
    out.add(new Models.ChatMessage(type, text));
}
```

ByteToMessageDecoder 维护累积缓冲，根据剩余数据、读取进展与输出情况循环调用 decode。一次 decode 是解析步骤，不等于一次 Socket read，也不天然等于一条业务请求。没有足够数据时，手写分帧逻辑应保留必要状态或不消费未完整数据，等待后续输入。

此处 out 是 List<Object>，不是出站编码器的 ByteBuf out。加入一个对象就产生一个输出，加入多个则逐个传播；没有结果时不会无条件把原 ByteBuf 再交给业务。父类负责传播，通常不要重复 fire 同一对象。

上面的“缺少类型字段”判断不能被视为已覆盖所有异常输入：ByteToMessageDecoder 的正常解析循环通常只对可读输入调用 decode，空帧未必进入该方法。因此，N 必须至少为 1 等协议合法性应在能检查该条件的层明确校验，不能只依赖此空缓冲分支。当前只完成源码与规则核对，空帧、超长帧等异常路径未实测。

## 5. 重复输出与乱码为何出现

错误写法：

```java
byte type = in.readByte();
String text = in.toString(StandardCharsets.UTF_8);
out.add(new Models.ChatMessage(type, text));
```

readByte 只消费类型；toString 不移动读索引。父类看到仍有可读数据且本轮取得进展，可能继续解析剩余正文：

| 次数 | 被读成 type 的字节 | 被当成正文的内容 |
|---|---|---|
| 第一次 | 1，真正类型 | hello |
| 第二次 | 104，即 h | ello |
| 第三次 | 101，即 e | llo |

中文会被从 UTF-8 字符中间重新解释，产生乱码或替换字符。问题在于解析位置错误，不是换一个字符集就能修好。

正确做法是消费正文，如 readBytes(content)；也可在 toString 后跳过对应可读字节。必须以已正确分帧为前提，不能把原始流中的全部剩余字节都当作一条正文。

## 6. 解码器选择与状态生命周期

| 方案 | 适用理解 |
|---|---|
| ByteToMessageDecoder | 面向字节累积与多步解析，依靠读索引进展循环；实例不可跨连接共享 |
| MessageToMessageDecoder<ByteBuf> | 将已经分帧的一项 ByteBuf 消息转换成业务对象，默认释放匹配输入，不按剩余字节做相同的累积循环 |

Message 指 Pipeline 中的一项数据，可以是 ByteBuf、String 或业务对象。已分帧场景使用 MessageToMessageDecoder 更直接，但不是必须替换；保留当前 ByteToMessageDecoder 并正确消费帧内容同样能处理合法帧。

若输出仍共享输入 ByteBuf 的底层内容，需要保留对应引用，不能让父类释放后输出失效；输出独立 String 或不持有该缓冲区的普通对象则不同。

在 initChannel 中 new Decoder 时，同一连接后续消息复用同一个实例。成员状态会持续保留：用 type=-1 表示阶段却忘记重置，可能错过下一帧类型；固定数组还要维护写入位置、有效长度和容量，不能始终覆盖末尾元素。已有前置分帧时，局部 type 与按帧分配的正文数组即可完成转换，无需再造多余的跨消息状态机。
