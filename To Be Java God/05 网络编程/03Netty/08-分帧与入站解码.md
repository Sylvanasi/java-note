# 08｜分帧与入站解码

## 1. 分帧与解码是两步

```text
原始字节流
    ↓ 分帧：确定一条消息的完整字节范围
完整一帧 ByteBuf
    ↓ 解码：读取字段并还原对象
ChatMessage
```

编码器写入一个 ByteBuf，不保证接收方恰好一次读到它。接收端必须按协议累积和提取消息。

## 2. 收到一部分时怎么办

目标消息：

```text
00 00 00 06 | 01 | 68 65 6c 6c 6f
```

先收到长度、类型和 he 时，已知还差 3 字节，所以先保留，等 llo 到齐再输出完整帧。

如果连前 4 字节长度字段都没齐，就先等待长度字段完整。一次输入包含多条消息时，也要逐条提取。

## 3. LengthFieldBasedFrameDecoder 的配置

```java
new LengthFieldBasedFrameDecoder(1024, 0, 4, 0, 4)
```

| 参数 | 本例值 | 含义 |
|---|---|---|
| maxFrameLength | 1024 | 整帧最大字节数，包含长度字段 |
| lengthFieldOffset | 0 | 长度字段位于帧开头 |
| lengthFieldLength | 4 | 用 4 字节读取长度值 |
| lengthAdjustment | 0 | 本协议无需额外修正长度 |
| initialBytesToStrip | 4 | 输出前跳过最前面的 4 字节 |

对本协议：

```text
实际完整帧长 = 长度值 N + 4
```

N 已包含类型和内容，因此不再额外给 lengthAdjustment 加 1。

## 4. 是否自动去掉长度信息

去不去掉由最后一个参数控制。

```text
输入：[长度4字节][类型][内容]
最后参数=4 → 输出：[类型][内容]
最后参数=0 → 输出：[长度4字节][类型][内容]
```

分帧器输出仍是 ByteBuf，不会自动生成 ChatMessage。

## 5. 本实验保留 ByteToMessageDecoder

前提：它前面已经按协议正确分帧，每次输入包含类型和该条消息的完整正文。

```java
public class ChatMessageDecoder extends ByteToMessageDecoder {
    @Override
    protected void decode(ChannelHandlerContext ctx,
                          ByteBuf in,
                          List<Object> out) {
        if (!in.isReadable()) {
            throw new CorruptedFrameException("消息缺少类型字段");
        }

        byte type = in.readByte();
        byte[] content = new byte[in.readableBytes()];
        in.readBytes(content);

        String text = new String(content, StandardCharsets.UTF_8);
        out.add(new Models.ChatMessage(type, text));
    }
}
```

这里的长度已经被分帧器去掉；剩余字节全是类型和正文。若取消前置分帧，就不能用“全部剩余字节是一条正文”的假设。

## 6. ByteToMessageDecoder 会循环调用 decode

它维护输入累积，根据输入是否还有数据、读取进度、输出情况等条件继续解析。

如果每次产生结果且仍消费了部分数据，它可能继续调用 decode，直到数据耗尽或需要等待更多输入。若输出了结果却完全不消费数据，框架也可能报解码未取得进展的异常。

因此 decode 是一个解析步骤，不代表一次 Socket read，也不天然等于一次完整业务请求。

## 7. 重复输出和乱码的根本原因

曾出现过这种代码：

```java
byte type = in.readByte();
String text = in.toString(StandardCharsets.UTF_8);
out.add(new Models.ChatMessage(type, text));
```

readByte 移动读指针；toString 不移动。于是第一次读出类型后，正文 hello 仍未消费：

```text
第一次：type=1，   content=hello
第二次：type=104， content=ello   // h 被读成类型
第三次：type=101， content=llo    // e 被读成类型
……
```

中文的 UTF-8 字节被逐个错读，会从字符中间开始解码，出现替换字符和乱码。

解决方式是正确消费正文，例如上面的 readBytes(content)，或在 toString 后 `in.skipBytes(in.readableBytes())`。

## 8. 为什么 MessageToMessageDecoder 也能用

Message 指 Pipeline 中的一项数据，ByteBuf、String、ChatMessage 都可以是 Message。

```text
MessageToMessageDecoder<ByteBuf>：一份 ByteBuf → 一份业务对象
```

它会对匹配的输入对象调用 decode 并管理输入释放，不按输入剩余字节进行 ByteToMessageDecoder 那样的累积解析循环。

当前已分帧的场景可以使用它，但不是必须替换。保留 ByteToMessageDecoder 并正确消费本帧字节，同样可以工作。

## 9. out.add 与向后传播

decode 的 out 是 `List<Object>`，不是编码器里的 ByteBuf out。

- 没添加结果：没有这次对应的解码结果向后传播。
- 添加一个对象：框架向后传播一个结果。
- 添加多个对象：框架逐个传播。

父类负责传播，不是 decode 一返回就无条件把原始输入再交给业务 Handler。

## 10. 实例、局部变量与状态

在 initChannel 中 new Decoder 时，同一连接的多次通信复用同一个 Decoder。

成员变量会持续保留。如果用 `type=-1` 当状态，读取一次后不重置，就可能跳过下一条消息的类型读取。使用固定数组也要维护实际写入位置、有效长度和容量；不能总写 content[content.length-1]。

当前协议已有前置分帧，用局部 type 和按本帧长度分配的 byte[] 就能直接完成转换。
