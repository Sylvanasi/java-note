# 11｜写缓冲与背压

![[附件/知识总览/11-写缓冲与背压.svg]]

## 1. 两端 Channel、积压与 TCP 窗口

一条 TCP 连接在两端各有一个本地 Channel。服务端 ChatHandler 中的 `ctx.channel()`，是服务端用于与当前客户端通信的连接 Channel，不是监听端口的 Channel，也不是客户端程序里的 Channel。

服务端与客户端各自拥有本地连接 Channel 和事件循环组，通过 TCP 连接通信，不共享 Channel 或线程组实例。

服务端和客户端分别 new 自己的 NioEventLoopGroup，不共享实例。服务端 workerGroup 配置为一个线程时，服务端的多个连接 Channel 可以共用同一个 NioEventLoop。

### 1.1 积压发生在哪里

应用提交数据的速度超过实际排出速度时，尚未排出的数据不断增加，这就是发送积压。

需要区分两个位置：

数据先进入进程内 Netty 待发送缓冲，经 flush 和 Socket 写入交给本地 TCP 发送缓冲，再通过 TCP 到对端接收缓冲，最后由对端应用读取。每一步的完成不能替代下一步。

Netty 中的积压消退，表示数据已从它的待发送缓冲中排出，不表示客户端业务已经收到或处理。

积压可能来自客户端读取慢、网络发送受限、应用短时突发发送，或应用只 write 而迟迟不 flush。不能仅凭积压认定 TCP 发生拥塞。

### 1.2 与 rwnd、cwnd 的关系

- rwnd：接收方通告的接收窗口。客户端读取慢，可能导致接收缓冲逐渐填满、rwnd 变小，这是流量控制。
- cwnd：发送方的拥塞窗口，用于拥塞控制。拥塞窗口及尚未确认的在途数据会影响继续发送的额度。

粗略理解，在途数据受 min(rwnd, cwnd) 约束。TCP 发送受限，可能使本地 TCP 发送缓冲空间不足，进而让 Netty 的数据无法及时写入 Socket。

但 Netty 的 isWritable 不直接查询 rwnd、cwnd，也不是“TCP 窗口是否为零”的判断。

## 2. 背压信号、高低水位与事件

背压是：下游处理不过来时，把压力反馈给上游，让上游减少或暂停生产、提交数据的机制。

- 积压：数据排不出去而累积的现象。
- 背压信号：通知上游已经出现发送压力。
- 响应背压：业务收到信号后减少或暂停提交。
- 恢复：压力减轻后继续处理。

仅打印不可写日志，属于观察信号，还没有完成发送控制。

### 2.1 高低水位与 isWritable

可以为服务端接受的连接设置：

```java
bootstrap.childOption(
        ChannelOption.WRITE_BUFFER_WATER_MARK,
        new WriteBufferWaterMark(1024, 2048)
);
```

需要的类型来自 io.netty.channel：

```java
import io.netty.channel.ChannelOption;
import io.netty.channel.WriteBufferWaterMark;
```

| 条件 | 因水位产生的状态变化 |
|---|---|
| 待发送积压超过高水位 2048 字节 | true → false |
| 变为 false 后，积压降到低水位 1024 字节以下 | false → true |
| 积压位于两个水位之间 | 保留此前的水位状态 |

采用高低两个阈值，避免状态在一个临界点附近频繁来回切换。水位不是定时器，状态变化没有最短等待时间。

这里的积压按 Netty 的待发送大小估算机制统计，也会计入管理开销，不仅是正文长度。消息载荷长度与待发送计数的增量可能不同，因为计数还包含管理开销；具体数值取决于实现、配置和消息类型。

isWritable 是本地发送压力的状态查询，不保证下次写立即完成，也不能替代 isActive 等连接状态判断。除了水位，Netty 的用户自定义可写标记等机制也可能影响该状态。

### 2.2 状态变化与事件通知

```java
@Override
public void channelWritabilityChanged(ChannelHandlerContext ctx)
        throws Exception {
    System.out.println(
            ctx.channel().remoteAddress()
                    + "，当前是否可写："
                    + ctx.channel().isWritable()
    );

    ctx.fireChannelWritabilityChanged();
}
```

关系是：Netty 更新可写状态 → 发出状态变化事件 → Handler 收到回调 → 代码通过 isWritable 读取当前状态。

- isWritable 是查询，不会主动触发这个回调。
- 回调是事件通知，不是定时检查，也不是每条消息发送后都执行。
- fireChannelWritabilityChanged 将事件继续传给后面的 Handler。
- 回调参数不携带变化瞬间的状态快照；Handler 在其他执行器上排队执行时，读取到的可能已是随后变化后的状态，日志不一定严格交替打印 false、true。

### 2.3 从信号到响应的完整闭环

完整反馈闭环包括：应用提交产生积压，超过高水位后变为不可写，状态变化事件通知业务暂停或减量；已提交数据经 flush 和 Socket 排出，低于低水位后恢复可写，再唤醒业务继续提交。

业务不响应信号也可以继续调用 write，Netty 不会因为 false 自动禁止追加。这里的“停止写入”指业务主动停止提交。

## 3. 每个接收连接的队列与执行器

以群聊服务为例：每条连接安装独立的 PendingWriteHandler，暂存发往该连接对端的消息，在可写状态恢复后继续发送。

服务端 Pipeline 的添加顺序：

Pipeline 按添加顺序依次配置 IdleStateHandler、长度分帧器、ChatMessageDecoder、StringEncoder、PendingWriteHandler，以及使用 businessGroup 的 ChatHandler。

出站方向相反：

群发到目标 Channel 后，出站先经过该连接的 PendingWriteHandler，再由前面的 StringEncoder 编码，最后交给底层待发送缓冲和 Socket。

在 initChannel 中为每条连接 new PendingWriteHandler，因此每个连接各有一个 Handler 实例、一份队列。普通成员变量并非天然“每连接一份”，是否隔离取决于实例创建和共享方式。

业务 Handler 专注心跳与群聊，发送 Handler 专注当前接收连接的排队和背压。群聊中的某个接收者慢，不应直接阻塞其他接收者。

### 3.1 同一个 Channel，不同执行器

在上述 Pipeline 配置中，ChatHandler 指定了 DefaultEventExecutorGroup，PendingWriteHandler 没有指定业务执行器，使用该 Channel 的网络 EventLoop。

| 对象 | 作用 |
|---|---|
| NioEventLoop | 处理 Selector、网络 I/O、提交的任务 |
| 业务 EventExecutor | 执行业务回调和任务，不监听 Selector |

同一条连接的两个 Handler 取得的是同一个 Channel，并不是各有一个 Channel。业务执行器有任务队列和执行循环，但类型上不是负责网络 I/O 的 NioEventLoop。

跨线程出站时，Netty 把处理任务提交给目标 Handler 的执行器。PendingWriteHandler 的 write、可写状态变化回调、channelInactive 都在同一个网络 EventLoop 上串行执行。

“串行”表示不会并行执行这几个回调，不代表业务线程不能同时提交新任务，也不代表禁止当前调用栈中的同步嵌套调用。

## 4. 有界队列与写入分支

待发送队列需要同时保存消息内容和这次写入对应的 Promise：

```java
private static final int MAX_PENDING_MESSAGES = 100;

private record PendingMessage(String content, ChannelPromise promise) {}

private final Queue<PendingMessage> pendingMessages =
        new ArrayBlockingQueue<>(MAX_PENDING_MESSAGES);
```

当前容量限制是 100 条消息，不是总字节数或等待时长的上限；大消息仍会增加内存压力。使用有界队列可以直接用 offer 的返回值判断是否满，不必先检查 size。不要使用阻塞式 put：等待队列空位会占住网络线程。

写入分支示例：

```java
@Override
public void write(ChannelHandlerContext ctx, Object msg,
                  ChannelPromise promise) throws Exception {
    if (!ctx.channel().isActive()) {
        promise.tryFailure(new ClosedChannelException());
        return;
    }

    if (ctx.channel().isWritable() && pendingMessages.isEmpty()) {
        ctx.write(msg, promise);
    } else {
        if (!pendingMessages.offer(
                new PendingMessage((String) msg, promise))) {
            promise.tryFailure(
                    new IllegalStateException("待发送队列已满")
            );
            ctx.close();
        }
    }
}
```

上述示例假定出站消息为 String，因此队列按 String 保存。若缓存 ByteBuf 等引用计数对象，还需要设计所有权转移、释放和异常清理，不能直接套用此实现。

关键分支：

- 连接已失活：本次写入失败，直接退出，不能重新进入暂存队列。
- 可写且队列为空：直接交给后续出站节点。
- 不可写或已有历史消息：新消息进入队尾。
- offer 返回 false：本次消息没有入队，设置失败并关闭当前慢接收连接。

“队列为空”的条件用于防止新消息越过已经排队的旧消息。不能在直接写入后再无条件入队，否则补发时会重复发送。

## 5. 恢复可写与排空边界

恢复发送的示例：

```java
@Override
public void channelWritabilityChanged(ChannelHandlerContext ctx)
        throws Exception {
    while (ctx.channel().isWritable() && !pendingMessages.isEmpty()) {
        PendingMessage pending = pendingMessages.poll();
        ctx.write(pending.content(), pending.promise());
    }

    ctx.flush();
    ctx.fireChannelWritabilityChanged();
}
```

执行过程：

每轮先检查可写和队列状态，再 poll 最旧消息并携带原 Promise 写出；下一轮重新检查。不可写时停止追加，剩余消息保留，仍对已经提交的部分执行 flush。

超过高水位的那次 write 已经提交，在下一轮检查时才停止。高水位是反馈阈值，不是严格禁止超出的内存硬上限。

本示例在循环结束后执行 flush；即使因为不可写停止追加，也要让已提交数据有机会排出。其他实现可以按批次 flush，关键是不能把已提交的数据一直留在未 flush 状态。flush 只是触发发送，不保证立即排空或立刻恢复可写。

仅在 write 中检查状态不够：如果暂停后没有新消息，就没有新的 write 触发处理，需要可写状态变化事件唤醒旧消息发送。

这里用 ctx.write 向当前节点之前的出站 Handler 传播。若在当前发送 Handler 内用 channel.write，会从 Pipeline 尾部重新经过自身，可能再次入队。

该示例说明恢复发送的基本过程。高吞吐场景需要限制单次处理量，通过续批调度避免长期占用 EventLoop；还应防止 flush 引起同步事件回调时重复进入排空逻辑。

## 6. Promise 的保存、透传与完成

调用方提交消息后拿到 Future：

```java
ChannelFuture future = channel.writeAndFlush("你好\n");
future.addListener(f -> {
    if (f.isSuccess()) {
        System.out.println("写入成功");
    } else {
        System.out.println("写入失败：" + f.cause());
    }
});
```

Promise 用于设置这次操作的结果，Future 用于观察结果。Pipeline 传播时携带对应 Promise，业务 Handler 不应随意丢弃它。

调用者取得 Future 后，发送 Handler 必须让消息与原 Promise 一起暂存；补发时一并透传，拒绝或关闭时完成为失败。Future 结果记录后通知监听器。

- tryFailure 是服务端程序内部的操作结果通知，不会向客户端发送文本通知。
- 没有监听器时结果仍会被记录。
- 不要在消息刚入业务队列时调用 trySuccess，那会提前把尚未实际完成的写操作当作成功。
- 本地写成功不等于对端收到、显示或业务处理成功；可靠投递需要客户端业务 ACK。

## 7. 连接关闭与队列清理

### 7.1 已关闭也会不可写，不能误当成暂时背压

对于 NIO Socket Channel，关闭时底层 outboundBuffer 被置空，isWritable 返回 false。这不是发送积压触发的不可写。

因此 false 可能意味着：

| 情况 | 处理方式 |
|---|---|
| 连接存活、暂时发送积压 | 排队等待恢复 |
| 连接已关闭 | 立即失败，不等待恢复 |

入口先检查 isActive，是为了保护我们自己的暂存逻辑。不能只看到 false 就把所有消息塞进队列。

### 7.2 为什么清理完还可能执行 write

channelInactive 先在网络 EventLoop 上清理队列，但业务线程仍可能随后提交写任务；网络线程顺序执行该任务时，入口必须检查失活并失败返回。这里是先后执行，不是两个回调并行。

不是 write 与 channelInactive 在网络线程上并行执行，而是清理前后仍可能有跨线程任务提交和执行。关闭对象不等于所有持有者立刻停止调用它。

如果消息继续交给 Netty 底层，已关闭连接的写入会被拒绝，Promise 会失败。但如果我们先把它截留在自己的队列中，Netty 底层就无法替它完成结果。

### 7.3 清理原有待发送消息

```java
@Override
public void channelInactive(ChannelHandlerContext ctx) throws Exception {
    PendingMessage pending;

    while ((pending = pendingMessages.poll()) != null) {
        pending.promise().tryFailure(new ClosedChannelException());
    }

    ctx.fireChannelInactive();
}
```

清理只针对仍在自己队列里的项；已经交给底层的写操作由 Netty 管理。

重连确实会创建新的 Handler 和空队列，但新连接不会替旧消息完成 Promise。不清理可能让旧 Future 一直未完成，调用方监听器不执行、无超时的等待迟迟不结束。

不清理不等于必然永久内存泄漏：旧对象整体无外部引用时仍可被 GC；如果旧 Channel、Handler 等仍被持有，队列引用会延长消息和 Promise 的存活。主动清理既结束操作结果，也解除队列持有的引用。

### 7.4 return、ctx.write、ctx.close 的区别

| 语句 | 含义 |
|---|---|
| return | 结束当前 Java 方法，不关闭连接 |
| ctx.write(msg, promise) | 将本次消息交给下一个出站处理节点 |
| ctx.close() | 发起关闭操作，沿出站方向传播；不会自动退出当前 Java 方法 |

未调用 ctx.write 就直接 return，本次消息不会继续传播。先调用了 ctx.write 再 return，不能撤销已经转发的写入。

方法自然结束也不会自动转发消息。close 是另一个出站操作，不会自动转发当前消息，也不会替当前写入 Promise 设置结果。

连接已关闭时，我们只需要将本次写入失败并 return；队列满时连接可能还活着，close 是主动采用的过载处理策略。

## 8. 群发结果与失败目标

一条业务消息只需要发起一次广播，并对这次返回的 Future 添加监听器：

```java
ChannelGroupFuture future = online.writeAndFlush(
        "服务端已收到：" + ctx.channel().remoteAddress()
                + ":" + msg.content() + "\n"
);

future.addListener(f -> {
    if (f.isSuccess()) {
        System.out.println("群发全部写入成功");
    }
});
```

连续调用两次 online.writeAndFlush 是两次独立广播，不是“第一次发送、第二次取得第一次的结果”。每个 Future 只对应其那次调用。

假设 A 发消息，广播给 A、B、C：

A 发消息时群发监听器捕获的 ctx 属于 A；若 B 的目标队列满，由服务端上 B 对应的 PendingWriteHandler 关闭 B 并失败其 Promise。组结果失败不意味着应该再次关闭 A。

不能在这里因为群发失败就 ctx.close，否则会把原发送者 A 也关闭。B 的队列满关闭策略，已经由服务端上 B 对应的 PendingWriteHandler 执行。

“每个接收者自己的 Handler”是服务端上对应连接的实例，不是客户端程序中的 Handler。只有队列满才采用关闭策略，暂时不可写不会立即断开。

ChannelGroupFuture 在组内操作完成后汇总结果：isSuccess 为 true 表示这次群发涉及的写操作全部成功。它不表示所有客户端业务都收到、显示或确认了消息。一个目标的写入仍暂存时，整体 Future 也可能尚未完成。

## 9. 不同业务的背压策略


| 数据性质 | 可以采用的策略 |
|---|---|
| 在线状态、实时位置 | 合并更新，只保留最新值 |
| 文件、大批量数据 | 暂停源头生产或读取，恢复后继续 |
| 可靠聊天消息 | 持久化并记录待投递进度，恢复或重连后补发 |
| 持续过慢的连接 | 设置等待时间、积压限制，必要时断开并重连同步 |

注意：

1. 内存待发送队列必须有界，否则只是把积压从 Netty 转移到业务内存。
2. 不可写分支直接跳过发送，相当于丢弃消息，不是“暂停后自动重试”。
3. 群发应判断每个目标 Channel 的状态。发送者的 ctx.channel 是否可写，不能代表其他接收者；online.writeAndFlush 不会替业务完成慢连接策略。
4. 恢复后分批补发，并持续检查可写状态，不要一次把所有历史消息重新塞入缓冲。
5. 不要在 EventLoop 上 sleep 或循环等待恢复，否则会阻塞负责发送和状态更新的网络线程。
6. 写 Future 成功不能代替客户端业务 ACK。

## 10. 当前实现与验证边界

本次核对 PendingWriteHandler 源码，已有失活入口检查、100 条 String 消息队列、可写恢复排空、原 Promise 透传和 channelInactive 清理。每条连接独立创建发送 Handler，业务线程与网络线程的配置与本文一致。

该实现仍是局部教学方案：没有单次排空批量上限、显式排空重入保护、队列等待超时、总字节预算，以及 Handler 被移除时的专门清理。String 强制转换依赖当前出站协议；不能直接承诺对任意 ByteBuf 或其他类型安全。本文只说明这些边界，不修改项目代码。

| 验证场景 | 应确认的结果 |
|---|---|
| 连接正常可写、队列为空 | 直接透传一次，不额外重复入队 |
| 不可写且队列未满 | 消息和原 Promise 一起保存，不提前成功 |
| 恢复可写 | FIFO 补发，继续检查水位，已写部分被 flush |
| 队列已满 | 新消息失败，并按当前策略关闭该接收连接 |
| 已排队时连接关闭 | 队列中每个 Promise 失败，移除队列引用 |
| 失活后新写任务到达 | 入口立即失败，不再等待恢复 |
| A 群发、B 持续过慢 | 处理 B 的积压，不误关 A；组 Future 按各目标结果完成 |

本次完成原文、源码及 Netty 水位规则核对，未重新运行慢读客户端、队列满、关闭后写入或重入等实验。以上是验收条件，不表示异常分支全部验证通过。
