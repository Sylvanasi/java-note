## 1. 协议、分帧与乱码

先观察消息边界与字段消费，再考虑字符集。以下是内容越来越短、type 变成字符数值的典型现象。

**典型现象：**

| 解析次数 | type | content |
|---|---|---|
| 首次 | 1 | hello |
| 第二次 | 104，即 h | ello |
| 第三次 | 101，即 e | llo |

检查 ByteToMessageDecoder 是否只 readByte 了类型，却用 toString 查看正文后没有消费正文。父类继续解析时，会把正文逐字节误当成下一条类型。

修正为读取实际字节：

```java
byte type = in.readByte();
byte[] bytes = new byte[in.readableBytes()];
in.readBytes(bytes);
out.add(new Models.ChatMessage(
        type, new String(bytes, StandardCharsets.UTF_8)));
```

前提是已经由前面的分帧器切出完整消息。

### 1.1 整帧长度异常

表示按照当前长度字段规则算出的整帧大小超过上限，不等于“实际业务文本一定很长”。

先检查：

1. 发送端是否经过正确编码器。
2. 收发双方的长度规则、字段位置和长度是否一致。
3. 是否用 nc 向二进制长度协议端口直接发送了普通文本。

本次出现过：

错误中的整帧大小为 `Adjusted frame length exceeds 1024: 1936945934`。

按当前参数扣除长度字段 4 字节，可得到长度值 1936945930，其字节为：

长度字段原始字节是 `73 73 73 0a`，即 s、s、s、换行。

这与输入普通文本 `sss` 再回车一致。先核对原始字节和协议，不应只靠调大上限掩盖格式错误。

### 1.2 中文乱码

按以下顺序定位：

- 字节是否在协议范围内完整。
- 是否误把正文里的字节当类型或长度。
- 是否先对不完整字符分段转了 String。
- 编码和解码是否一致使用 UTF-8。
- 是否用字符数替代了字节数。

先正确分帧，再对完整正文做 UTF-8 转换，能避免本实验中的字符跨读取片段问题。

## 2. 业务内容、重复发送与空行

**时间戳没有变化：**

检查生成消息对象和调用 System.currentTimeMillis 的位置。如果在周期任务外只生成一次对象，反复发送自然是同一份时间戳。

若每次任务都新建消息：

```java
scheduleAtFixedRate(() -> {
    var msg = new Models.ChatMessage(
            (byte) 1, "时间戳=" + System.currentTimeMillis());
    channel.writeAndFlush(msg);
}, 0, 12, TimeUnit.SECONDS);
```

则继续检查 Decoder 是否保留上次成员状态、是否重复解析旧数据，以及正在运行的进程是否已使用新代码。

同一个 Decoder 实例会复用，但正确的局部变量读取不会因此自动重复上次时间戳。

### 2.1 重复内容、空行与只有 PONG

- 两份业务内容：先数业务方法里 online.writeAndFlush 实际调用次数。
- 空行：检查正文自己带的换行与服务端附加的换行是否叠加。
- 只有 PONG：检查发送类型是否仍只有心跳 type=2。

不要仅凭多行控制台输出判断网络发生了重复投递。

## 3. 线程、异步结果与关闭对象

**main 已结束，进程仍在运行：**

默认 NioEventLoopGroup 使用非守护线程，自定义线程工厂可以改变此属性。main 返回不会自动关闭这些线程；连接失败或结束时应管理线程组关闭。

反过来，不要在某个普通客户端断开时就关闭整个服务端 workerGroup，因为其他连接还可能共用它。

### 3.1 对端关闭后 closeFuture 很快完成

closeFuture 监听本地 Channel 的关闭。常见默认 TCP 使用方式下，正常远端结束通常可及时被 I/O 检测，不必等待空闲阈值；半关闭配置需要另行区分。

先判断监听的是哪个 Channel：

| 来源 | 对象 |
|---|---|
| bootstrap.bind(...).channel() | 服务端监听 Channel |
| bootstrap.connect(...).channel() | 客户端连接 Channel |
| 服务端业务 Handler 的 ctx.channel() | 当前客户端对应的服务端连接 Channel |

### 3.2 传播返回但业务尚未执行

检查业务 Handler 是否指定 businessGroup。跨执行器提交任务后，外层 fireChannelRead 可以先返回，业务稍后执行。

finally 只保证当前 try 的收尾，不替异步任务等待完成。

## 4. 引用计数与资源生命周期

**release 后出现 IllegalReferenceCountException：**

检查是否重复释放、提前释放，或者 SimpleChannelInboundHandler 自动释放后又继续使用同一 ByteBuf。

额外 retain 必须有对应释放，但不能因为多了一个 Java 变量就认为自动多了一份引用计数。

如果原始 ByteBuf 已转换成 String 或普通对象，后面的业务不再需要原缓冲；不要为了等待所有业务结束而无意义保留原始内存。

### 4.1 传播返回时 refCnt 仍为 2

同步返回不保证下游释放。分帧器可能合法地保留未完成数据；额外 retain 的引用也还在。

应按谁持有、谁释放分析生命周期，不把某一次 refCnt 值直接等同于泄漏。

## 5. 配置、日志与源码核对

**配置改成 20 秒，日志仍说 6 秒：**

配置和日志字符串是两处独立代码。以真正的 IdleStateHandler 参数为准，同时更新日志文字，避免把显示文案当成实际阈值。

## 6. 统一排查顺序与专题入口

1. 确认正在运行的进程和代码版本。
2. 确认具体 Channel 与连接方向。
3. 查看分帧前字节范围，不移动读索引。
4. 核对字段规则、读索引与解码输出数量。
5. 核对业务状态、发送次数与换行。
6. 核对执行线程、异步结果与资源关闭。
