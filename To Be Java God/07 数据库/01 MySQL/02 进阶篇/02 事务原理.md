# 事务原理

![[附件/知识总览/02-事务原理.svg]]

图中 1—8 对应正文小节。以下聚焦普通 InnoDB 持久表；提交时的持久性结论需结合刷盘配置与存储设备保障。

## 1. 事务特性与日志职责

- **原子性（Atomicity）**：事务的修改作为一个整体提交或回滚，undo log 提供撤销修改所需的信息。
- **持久性（Durability）**：已经成功提交的修改不能因故障而丢失，redo log 是 InnoDB 实现这一保障的核心机制。
- **隔离性（Isolation）**：通过锁、MVCC 等机制控制并发事务的相互影响，具体行为取决于隔离级别。
- **一致性（Consistency）**：事务执行前后应满足数据约束与业务规则。数据库事务机制和约束提供保障，业务代码仍需正确表达规则，例如转账的扣款与入账必须成对执行。

**redo 主要保证持久性，崩溃恢复是实现这一保障的机制；undo 支持回滚，保证原子性，同时为 MVCC 提供旧版本信息。**

## 2. 为什么需要 redo log

InnoDB 按页管理数据，数据页默认大小为 16KB。更新记录时，通常先在 Buffer Pool 中修改对应的数据页；内存页与磁盘中的内容不同后，该页称为**脏页**。

如果每次提交都把修改过的所有数据页写回磁盘，会有两个主要开销：

- 写入量较大：只修改少量字段，也通常需要刷整个数据页。
- 位置分散：多个数据页可能位于不同位置，产生较多随机 I/O。

redo log 记录数据页的修改信息，通常比写整个数据页更精简，且以顺序追加为主。因此可以先保证相关日志持久化，再由后台择机刷数据页，降低提交时等待 I/O 的开销。

redo log 不是原始 UPDATE SQL 的副本，也不负责执行刷脏页。

## 3. redo log 的位置与提交流程

| 位置 | 所属层次 | 是否易失 |
|---|---|---|
| redo log buffer | MySQL 进程内存 | 进程退出或断电可能丢失 |
| 操作系统文件缓存（page cache） | 操作系统内存 | 系统崩溃或断电可能丢失 |
| 持久化存储 | 磁盘等存储设备 | 正确完成持久化后，可用于故障恢复 |

数据页刷盘与提交解耦，通常由后台推进，也可能因压力触发，可能发生在提交前，也可能发生在提交后。

**提交成功不意味着修改后的数据页已经落盘。** 即使磁盘数据页仍是 100，只要已提交修改所需的 redo 已经持久化，就能在故障后恢复为 80。

如果数据库已经提交，但成功响应尚未到达客户端就发生故障，客户端可能无法确定提交结果，需要查询确认，不能直接把超时等同于回滚。

## 4. 落盘不等于提交：WAL 与未提交数据页

必须区分三个动作：

| 动作 | 含义 |
|---|---|
| redo 日志落盘 | 修改信息已经可靠保存 |
| 数据页落盘 | 修改后的页已经写入数据文件 |
| 事务提交 | 数据库确认这组操作正式生效 |

redo 可以在事务尚未提交时落盘；未提交事务修改过的数据页也可以落盘。**日志或数据已经写入磁盘，不代表事务已经提交，也不代表其他事务就能读取这些修改。**

InnoDB 遵循 WAL（Write-Ahead Logging，预写日志）：

> 数据页落盘之前，必须先保证对应的 redo 日志持久化。

假设余额从 100 改为 80，事务尚未提交，修改后的数据页已经落盘，此时发生断电。恢复时仍需根据事务状态处理，利用 undo 信息撤销未提交事务的修改，恢复为 100。

因此，回滚不能简单理解为丢弃内存中的修改。

## 5. redo log 刷盘策略

参数 `innodb_flush_log_at_trx_commit` 控制提交时 redo 的写出与刷盘行为：

可以区分日志缓冲、操作系统缓存与持久化存储三个逻辑层次。write 写出不等于 fsync 等同步操作完成；具体 I/O 策略可能绕过某些缓存层次。

写入操作系统缓存仍然是在内存中，不等于完成持久化。

| 参数值 | 提交时的要求 | 后续行为 |
|---|---|---|
| 1（默认） | 写出并刷盘，提交成功前保证相关 redo 持久化 | 优先保障持久性 |
| 2 | 写出到操作系统缓存，不要求本次提交同步刷盘 | 通常约每秒刷盘 |
| 0 | 提交时不要求写出或刷盘 | 通常约每秒写出并刷盘 |

“约每秒”不是严格的时间保证，实际间隔可能受调度与配置影响；不能据此断言最多只丢一秒数据。

- 仅 MySQL 进程崩溃：进程内 redo log buffer 可能丢失，操作系统缓存通常仍在。配置 0 可能丢失近期已提交事务；配置 2 已写入操作系统缓存的 redo 通常能够保留。
- 操作系统崩溃或断电：两处内存都可能丢失，配置 0、2 都可能丢失近期已提交事务。
- 配置 1：在存储设备正确兑现刷盘要求的前提下，保证已成功提交事务的持久性。

“提交成功时，redo 已持久化”的表述以配置 1 为前提。配置 0、2 用较弱的持久性保障换取较少的提交刷盘等待。

## 6. undo log：如何撤销修改

undo log 保存撤销修改所需的信息，支持事务回滚：

| 原操作 | 撤销效果 |
|---|---|
| INSERT | 撤销插入的记录 |
| UPDATE：余额 100 → 80 | 恢复修改前的余额 100 |
| DELETE | 恢复删除前的记录状态 |

这些是撤销效果的示意。**undo log 不是简单保存、插入或执行一条反向 SQL**，而是由 InnoDB 根据内部 undo 记录撤销修改。

例如转账中扣款已经完成，入账失败，数据库需要利用 undo 信息撤销本次事务的修改，而不是只停止执行后续语句。

### undo 页也受到 redo 保护

undo 信息本身也存储在页中。对于普通持久表，对 undo 页的修改同样会产生 redo 日志：

业务数据页将余额改为 80，这次页修改产生 redo；undo 页保存恢复余额 100 所需的信息，对 undo 页的修改也产生 redo。两类页的修改都需要恢复保障。

如果修改后的业务数据已落盘，而 undo 信息却丢失，就无法可靠回滚。redo 保护 undo 页修改，使故障后能够恢复必要的撤销信息。

这不是无限递归记录：产生 redo 日志本身不需要再生成 undo 日志。

### 两种 undo 类型

| 类型 | 对应操作 | 用途与提交后的处理 |
|---|---|---|
| insert undo log | INSERT | 用于回滚插入，提交后即可释放 |
| update undo log | UPDATE、DELETE | 用于回滚，也供 MVCC 重建旧版本；提交后可能需要保留 |

插入前记录不存在，不需要借助 insert undo 重建一条更早的记录版本。

更新和删除前则存在旧数据。即使修改事务已经提交，其他事务的快照读取仍可能需要这些旧版本，因此相关 update undo 不能立即清理。

## 7. 日志的清理与空间复用

### redo：由 checkpoint 推进控制复用

redo 空间不是按事务提交后逐条删除的。

当相关修改已经可靠写入数据页，InnoDB 可以推进 checkpoint（检查点）；检查点之前不再被恢复需要的 redo 空间可以被覆盖复用。

**事务提交不是 redo 空间可立即复用的充分条件。** 如果数据页尚未落盘就覆盖了唯一的恢复信息，可能破坏已提交修改的持久性。

### undo：由旧版本需求决定清理时机

事务提交后，不再需要为它执行回滚，但相关 update undo 可能仍被其他事务的快照读取需要。在事务已提交、也没有快照再需要这些历史等条件满足后，purge 才能清理相关历史信息。

释放 undo 信息也不等于 undo 表空间文件马上缩小；空间可以留给后续事务复用。

### 长事务为什么会导致历史积压

例如事务 A 长期持有需要余额 100 的快照；随后 B 将余额改为 80 并提交，C 改为 60 并提交，D 改为 40 并提交。

只要 A 仍需要旧版本，就必须保留重建该版本所需的 undo 历史。B、C、D 已经提交，也不能直接清掉这些历史。

即使事务只查询、不修改，也可能因为长期持有旧快照而阻碍清理。不是所有执行过 BEGIN 的事务都会如此，关键在于是否持有仍需要相关历史的快照。

业务上应尽量缩短事务范围，避免在事务中等待用户操作，或执行不必要的耗时远程调用。

## 8. 易混淆点

- redo 主要保证持久性，不负责把脏页刷到磁盘。
- redo 在执行过程中持续产生，不是提交时才开始记录，也不只包含已提交事务的修改。
- redo 落盘、数据页落盘和事务提交是不同动作。
- 未提交数据页可以落盘，undo 使其仍能被撤销。
- undo 不是反向 SQL；UPDATE 和 DELETE 都使用 update undo。
- 事务提交后，redo 和 undo 不一定立即可以清理。
- redo 与 undo 的配合不等于仅靠日志就能保证所有业务规则正确。
