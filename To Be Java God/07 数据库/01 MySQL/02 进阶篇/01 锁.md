# InnoDB 锁

![[附件/知识总览/01-锁总览.svg]]

图中 1—6 对应正文小节。以下主要讨论 MySQL InnoDB，在 RC（读已提交）、RR（可重复读）下区分快照读与加锁读取。具体加锁范围还取决于索引、执行计划和版本。

## 1. 锁模式：S 与 X

锁模式回答“哪些访问可以同时进行”，锁范围回答“保护什么”，两者可以组合。

| 已持有的锁 | 其他事务申请 S | 其他事务申请 X |
|---|---|---|
| 共享锁 S | 兼容 | 等待 |
| 排他锁 X | 等待 | 等待 |

共享锁允许多个事务共同持有，但阻止其他事务获得修改所需的 X 锁。排他锁可类比 Java synchronized 的互斥性；共享、排他两种模式则可类比读写锁。但数据库还有快照读，不能据此认为 X 锁会阻止所有读取。

FOR SHARE 只查询、不修改数据，但不意味着当前事务被设成只读。当前事务之后仍可申请 X 锁进行更新；多个事务同时持有 S 锁再升级，可能死锁。

意向锁是表级协调标记：加记录 S 锁前取得 IS，加记录 X 锁前取得 IX，帮助协调表级锁与行级锁。IX 不等于整表被排他锁定，多个事务可同时持有 IX，再修改不同记录。InnoDB 自动管理这些锁。

## 2. 读取方式与锁等待

| 操作 | 读取方式与锁 |
|---|---|
| RC、RR 下普通 SELECT | 通常为快照读，按可见性读取版本 |
| SELECT ... FOR SHARE | 当前读，申请 S 锁 |
| SELECT ... FOR UPDATE | 当前读，申请 X 锁 |
| UPDATE、DELETE | 对目标记录按当前读处理，申请 X 锁 |

“当前读”是读取方式，没有“当前锁”这一锁模式。当前读不是必然等待，而是在申请的锁与其他事务持有的锁冲突时等待。快照读不因这些记录 S/X 锁等待，但不能推广为任何情况下都不阻塞，例如仍可能受元数据锁影响。

事务 A 将余额100扣成90但未结束，B执行数据库内扣20的 UPDATE：B等待；A提交后，B基于90扣至70；A回滚后，B基于恢复后的100扣至80。B不会拿旧快照100覆盖计算结果。

相关记录锁通常持有至事务提交或回滚，不是 SQL 执行完就释放。这里描述需要保留的事务锁；RC 扫描中不匹配记录的锁等存在提前释放规则。

## 3. 记录、间隙与临键锁

假设索引已有10、20、30：

| 类型 | 保护范围 | 作用 |
|---|---|---|
| 记录锁 Record Lock | 索引记录20 | 限制对该记录的冲突访问 |
| 间隙锁 Gap Lock | (10,20) | 阻止向该间隙插入索引项，不包含端点记录 |
| 临键锁 Next-Key Lock | (10,20] | 记录20与其前方间隙的组合 |

**记录锁定义是锁索引记录，不是“必须通过唯一索引精准查询”。** 一条 SQL 可以锁多条索引记录，记录锁也不限于主键。行级锁是更宽泛的说法，不能与“只锁一条数据”画等号。

**临键锁从范围看等于前方间隙锁加右端记录锁**，不一定是数据库先加一个再补另一个。20对应的临键范围是(10,20]，30对应的是(20,30]，不是在记录左右任选一侧。

只持有(10,20)的间隙锁时，插入15会等待；普通查询15不会因它等待。该间隙锁本身不锁住10、20的记录。修改端点记录且不改变相关索引值，不会仅因这个间隙锁而阻塞。

## 4. SQL 如何决定锁范围

锁由 InnoDB 根据语句、隔离级别及实际索引扫描自动设置，没有单独的 GAP LOCK 命令。

**唯一索引等值命中已有记录：** 例如 id 为主键，执行：

```sql
BEGIN;
SELECT * FROM account WHERE id = 20 FOR UPDATE;
```

可以只对找到的主键索引记录加 X 记录锁，不锁相邻间隙。其他事务修改20或对20申请S/X锁需要等待；插入15不因该记录锁受阻。

**RR 下唯一索引等值未命中：**

```sql
SELECT * FROM account WHERE id = 15 FOR UPDATE;
```

已有10、20、30时，会保护15所在的(10,20)间隙。边界是相邻已有索引记录，不按整数运算取11或19，也不是跨过已有记录的(0,30)。因此插入12、15、18都会等待。若已有10、12、20、30，15所在间隙就变成(12,20)。

**普通索引碰巧只匹配一条：** WHERE value=10 不能仅按结果行数判断锁范围。唯一索引保证最多一条，普通索引只是在当前碰巧一条；RR下普通索引的加锁查询通常还涉及间隙保护。没有适用索引时可能扫描、锁住更多记录。

**查询范围不等于一个锁的形状：** WHERE id>=10 AND id<20 的条件范围是[10,20)，但不能称为一个左闭右开的临键锁。记录10与(10,20)间隙可以组合保护该范围；实际是否额外涉及边界记录，要按执行情况核对，不能直接由 WHERE 推断完整锁集合。

**RC 与 RR：** RR的加锁范围查询通常使用间隙/临键保护；RC普通搜索扫描通常不使用间隙锁，因此别人可能插入范围内新记录。RC下外键、重复键检查等仍可能涉及间隙锁。只要实际已经持有冲突的间隙锁，插入就会等待，不存在“RC能绕过已持有间隙锁”的规则。

直接 INSERT 15 不等于给整个(10,20)加阻止其他插入的间隙锁；插入有插入意向锁等机制，本节未深入。

## 5. 开发中的悲观锁

必须先查询、判断再修改时，可以把查询改成 FOR UPDATE，并将整个过程放在同一个事务中：

```java
@Transactional
public void deduct() {
    int balance = 查询余额ForUpdate();
    if (balance >= 80) {
        更新余额(balance - 80);
    }
}
```

这是逻辑示意，事务注解需要有效地经过 Spring 代理，查询和更新使用同一事务。

A锁住账户并读取100；B在相同账户的FOR UPDATE处等待。A扣80并提交后，B获得锁，读到20，再判断不足。普通快照查询仍可读，其他账户通常不受该记录锁影响。所有执行同类“先查再改”的入口都需遵守并发协调方式，不能另有入口基于旧值覆盖更新。

对于简单条件更新，也可合并成一条原子 SQL：

```sql
UPDATE account
SET balance = balance - 80
WHERE id = 1 AND balance >= 80;
```

检查影响行数：1表示成功，0表示不存在或余额不足。该方案与先锁再查是两种实现方式，不能用“单条 SQL 原子性”替代对多语句加锁流程的理解。

生产中优先掌握事务边界、索引影响、及时释放锁；避免持锁期间调用耗时远程服务或等待用户操作。多个流程锁相同记录时统一顺序，例如转账无论方向如何，都先锁较小账户ID，再锁较大的。

## 6. 死锁检测与异常处理

死锁是循环等待，不是普通排队：

| 步骤 | 事务 A | 事务 B |
|---|---|---|
| 1 | 锁账户1 | |
| 2 | | 锁账户2 |
| 3 | 请求账户2，等待B | |
| 4 | | 请求账户1，等待A |

等待时仍持有之前的锁。A等B、B等A，双方无法推进。若双方都按先账户1、再账户2的顺序加锁，B可在第一步等待且尚未锁住账户2，就不会形成上述循环；这不保证消除所有其他死锁。

InnoDB通过事务锁等待关系检测环，可以涉及两个或更多事务。默认启用死锁检测；不是等很久才把它当成死锁。锁等待超时是另一机制。

检测到死锁后，InnoDB选择一个事务整体回滚，释放锁，打破循环。选择不是随机抽签，倾向回滚较小事务，官方用插入、更新、删除行数说明事务大小；不能把这一倾向当作业务保证，也不是谁后执行就回滚谁。

数据库错误：

```text
错误码：1213
SQLSTATE：40001
Deadlock found when trying to get lock; try restarting transaction
```

意思是“尝试获取锁时发现死锁；请尝试重新执行事务”。

Java执行SQL时，通过JDBC收到SQLException的具体子类；Spring/MyBatis等可能再包装或转换异常，具体类名依赖版本与配置，应检查底层错误码和原因链。

**被牺牲的是整个事务，不只是报错语句。** 同一事务中先前已经执行成功但未提交的InnoDB修改也会回滚。数据库已执行回滚，不是等Java的@Transactional收到异常后才撤销。

默认可让异常向外传播，使业务失败。需要重试时，仅针对允许重试的错误，有限次数并适当退避；在事务外控制重试，每次经事务代理开启新事务，重新完成整笔业务，不能捕获后只重试报错SQL。涉及数据库外副作用还需单独保证重试安全。
