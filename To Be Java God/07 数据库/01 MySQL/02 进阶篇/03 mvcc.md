# MVCC

![[附件/知识总览/03-MVCC.svg]]

图中 1—8 对应正文小节。本文讨论 MySQL InnoDB，快照读主要限定为读已提交、可重复读下的普通 SELECT；不将 SQL 标准的最低保障直接等同于 InnoDB 的实现。

## 1. MVCC 解决什么问题

事务 A 把已提交的余额 `100` 改成 `80`，尚未提交。此时另一个事务 B 查询，既不能读到未提交的 `80`，也不一定需要等待 A 完成：它可以读取符合可见性规则的旧版本 `100`。

**MVCC（多版本并发控制）通过历史版本与可见性判断，让快照读取和数据修改能够并发进行。** 这不代表所有读写都无须加锁；写操作和加锁读取仍需要锁协调。

三个部分各有职责：

| 部分 | 职责 |
|---|---|
| 当前记录及其事务编号 | 提供最新数据，标识最后修改它的事务 |
| Read View（读视图） | 提供判断版本是否可见的事务信息 |
| undo 与版本链 | 最新版本不可见时，按需重建更早版本 |

redo 主要用于持久性与崩溃恢复，不负责为快照查询选择版本。undo 除了支持回滚，还提供重建历史版本所需的信息。

## 2. 版本链：旧版本怎么找到

InnoDB 聚簇索引记录中，与版本查找相关的隐藏字段包括：

| 字段 | 作用 |
|---|---|
| `DB_TRX_ID` | 最后插入或修改该记录的事务编号，用来判断版本是否可见 |
| `DB_ROLL_PTR` | 回滚指针，指向相关 undo 记录，用来重建之前的版本 |

假设同一条记录依次发生以下修改：

| 版本 | 余额 | 修改事务编号 |
|---|---:|---:|
| 最早版本 | 200 | 12 |
| 中间版本 | 100 | 16 |
| 最新版本 | 80 | 24 |

当前记录保存最新的 `80`。借助回滚指针和 undo，可以重建 `100 / 事务16`，再继续重建 `200 / 事务12`。undo 不一定保存每个版本完整的一行副本，也不是反向 SQL。

读取时先检查最新版本。如果事务24对读视图不可见，就重建上一个版本；如果事务16可见，就返回 `100`，不再继续查找 `200`。

**版本检查发生在读取记录时，不是创建读视图时。** 找到第一个可见版本就停止；如果没有可见版本，这条记录对该快照不存在。新插入记录在插入前不存在，因此不能凭空重建出一条更早存在的记录。

历史信息不是永久保留；没有相关快照再需要时，purge 才能清理。长事务持有旧快照可能阻碍清理，详见 [[02 事务原理]]。

## 3. Read View：记录事务信息，不保存表的副本

Read View 不属于某个字段、某条记录或某张表。它是在特定时刻记录的一组事务信息，供读取时判断版本是否可见。

以下使用常见教学名称，示意 B 的读视图：

| 项目 | 示例值 | 含义 |
|---|---|---|
| `creator_trx_id` | 30 | 创建者自己的事务编号；示例假设 B 已获得编号 |
| `m_ids` | `[24, 27]` | 创建视图时，其他仍活跃的读写事务编号 |
| `min_trx_id` | 24 | 示例中的最小活跃事务编号 |
| `max_trx_id` | 31 | 创建视图时，下一个待分配的事务编号，不是当前最大已提交事务编号 |

以上是便于理解的命名，内部源码字段命名可能不同。纯只读事务不一定分配读写事务编号；活跃列表为空时，下界可取上界，不对空列表求最小值。

**它不需要提前知道以后查询哪些表，更不会在创建时加载所有表的数据。**

例如 B 在可重复读下先查询 A 表，建立读视图；之后事务32把 B 表的一条记录从 `100` 改成 `80` 并提交；直到事务快结束，B 才第一次查询 B 表。

此时才访问 B 表的数据，用已有读视图检查修改事务编号32。因为 `32 ≥ 31`，新版本不可见，再通过 undo 重建可见旧版本 `100`。

同一读视图可以用于多行、多个字段、多张 InnoDB 表；它提供共用的判断依据，数据和历史版本则在实际读取时按需访问。

## 4. 可见性：把版本事务编号与读视图对照

以第3节的读视图为例，对记录版本的修改事务编号 `trx_id` 判断：

1. 如果等于创建者自己的事务编号：自己之前语句产生的修改可见。
2. 如果小于 `min_trx_id`：创建视图前已提交，可见。
3. 如果大于等于 `max_trx_id`：属于视图建立后的事务，不可见。
4. 如果处于两者之间：在 `m_ids` 中不可见；不在列表中则可见。

| 版本修改事务编号 | 可见性 | 原因 |
|---:|---|---|
| 21 | 可见 | 小于24，在创建视图前已提交 |
| 24 | 不可见 | 在活跃列表中 |
| 26 | 可见 | 小于31，且不在活跃列表中 |
| 27 | 不可见 | 创建视图时活跃，后来提交也不会改变旧视图 |
| 30 | 可见 | 属于 B 自己的修改 |
| 32 | 不可见 | 大于等于31，即使现在提交了，对旧视图仍不可见 |

**小于上界不能单独证明可见，还要检查活跃列表。** 事务编号也不是提交顺序；编号较小的事务可能更晚提交。

读视图记录的是创建时的情况，不是查询时实时刷新的一份事务状态表。版本不可见时，继续沿版本链判断更早版本。

## 5. 隔离级别：何时创建、是否复用

读已提交与可重复读的 Read View 基本结构和可见性规则相同，主要区别在于创建与复用时机。

| 隔离级别 | 快照读使用的读视图 |
|---|---|
| 读已提交 | 每条快照查询语句建立新的读视图 |
| 可重复读 | 通常第一次快照查询建立，之后同一事务的快照查询复用 |

**普通 BEGIN 不等于立即创建读视图。** 可重复读下，普通 BEGIN 与第一次快照查询之间，其他事务提交的修改仍可能被第一次查询看到。显式使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 是主动建立一致性快照的特殊入口。

例如 B 第一次普通查询得到 `100`，随后 A 把余额改成 `80` 并提交，B 再次普通查询：

| 隔离级别 | 第二次结果 | 原因 |
|---|---:|---|
| 读已提交 | 80 | 新读视图可以看到 A 的提交 |
| 可重复读 | 100 | 沿用旧视图，A 的修改仍不可见 |

时间基准是**读视图创建时刻**，不能笼统说成“当前事务开启时刻”。

## 6. 快照读、当前读与自身修改可见

| 操作 | 读取方式 | 关键行为 |
|---|---|---|
| 普通 SELECT，读已提交或可重复读 | 快照读 | 按 Read View 选择可见版本 |
| SELECT ... FOR SHARE | 当前读、加锁读取 | 加共享锁 |
| SELECT ... FOR UPDATE | 当前读、加锁读取 | 加排他锁 |
| UPDATE、DELETE 对目标记录的处理 | 按当前读理解 | 基于当前记录处理，并加所需的锁 |

当前读不会沿用旧 Read View 选择一个历史版本来修改。碰到冲突锁时，通常需要等待其他事务提交或回滚；不是只要有其他事务在运行就必须等待。读已提交下 UPDATE 的扫描还存在半一致性读等细节，不将“当前读”简化成每个扫描步骤都完全一样。

**关键例子：同一读视图仍能看到自己的新修改。** B 使用可重复读，账户最初余额为100：

| 顺序 | 事务 B | 事务 A |
|---|---|---|
| 1 | 普通查询得100，建立读视图 | |
| 2 | | 改成80，提交 |
| 3 | 再次普通查询，仍得100 | |
| 4 | 执行 UPDATE account SET balance = balance - 10 WHERE id = 1，改成70 | |
| 5 | 再次普通查询，得到70 | |

第3步看不到 A 的80；第4步 UPDATE 以当前80为基础扣减；第5步看到的是 B 自己写入的70。**读视图没有更新，最新记录版本变成了自己的修改，因此可见。**

**单条更新与先查再改的区别：**

```sql
UPDATE account SET balance = balance - 10 WHERE id = 1;
```

两个事务都成功执行并提交该语句，且没有其他修改时，初始100最终得到80。数据库通过写锁协调对同一记录的修改。

如果程序先普通查询100，在程序里算出90，再执行 `UPDATE account SET balance = 90 WHERE id = 1`，两个事务可能都写入90，发生丢失更新。单条语句的原子性，不等于整个“先查、再算、再写”流程自动并发安全；当前读也不会纠正程序传入的旧计算结果。

## 7. 幻读：区分标准与 InnoDB 的读取场景

经典场景是：同一事务按相同条件查询，其他事务插入或删除并提交后，再查时符合条件的记录集合变化。以新增记录为例，第一次 `COUNT(*) WHERE id = 5` 为0，第二次变成1。

SQL 标准的可重复读最低保障不要求消除幻读；但不能据此断言 InnoDB 的可重复读在连续快照查询中一定出现幻读。

| InnoDB 可重复读场景 | 机制与结果 |
|---|---|
| 连续普通快照查询，自己未修改相关数据 | 复用读视图，其他事务新插入并提交的记录仍不可见 |
| 从一开始就使用加锁读取保护查询条件 | 所需的记录锁、间隙锁或临键锁保护相应范围，阻止冲突修改及插入 |

例如 B 普通查询 `id=5` 不存在，A 随后插入并提交，B 再普通查询仍不存在：它不是找到了某条旧记录，而是插入版本不可见、插入前记录不存在。

**自身更新后多出可见记录，不能直接当作上述经典幻读的例子。** 混用快照读与当前读得到不同结果，也不能据此认为旧快照被更新。这些结果变化与单纯由其他事务导致的两次相同快照查询变化要分开。

上述结论说明 InnoDB 在相应读取场景下通过 MVCC 或范围锁防止幻读，不代表可重复读等价于串行化，也不意味着事务内任意读写组合的结果永远不变。

## 8. 锁与串行化：比稳定快照更强的保障

FOR SHARE 与 FOR UPDATE 都属于加锁当前读。对同一记录，忽略超时和 NOWAIT 等特殊选项时：

| 已持有的锁 | 其他事务再 FOR SHARE | 其他事务再 FOR UPDATE 或修改 |
|---|---|---|
| 共享锁 | 可以兼容 | 冲突，需要等待 |
| 排他锁 | 冲突，需要等待 | 冲突，需要等待 |

这些限制针对冲突的加锁操作；读已提交、可重复读下的普通快照查询通常仍可读取可见版本。锁保护的具体范围取决于索引和查询条件，不能一概当成只锁一条记录。

**串行化要求并发事务成功执行的效果等价于某个串行执行顺序，保障比“快照稳定、不出现经典幻读”更强。** 它不要求全库每次只能运行一个事务。

在 InnoDB 串行化下，关闭自动提交的事务中，普通 SELECT 会隐式按 SELECT ... FOR SHARE 处理。显式多语句事务中的普通读取也会加共享锁；但自动提交下独立执行的普通 SELECT 自己就是一个只读事务，可以采用非加锁一致性读取，不能说所有 SELECT 无条件变成当前读。

例如 B 读取已有账户余额100后不结束，A 尝试修改该记录：

- 可重复读的普通快照查询不加这种读锁，A 可以修改并提交，B 继续看旧快照。
- 串行化的上述加锁查询持有共享锁，A 的写锁请求发生冲突，需要等待 B 结束。

更强的并发约束也意味着更多等待与死锁可能性。稳定的历史快照和可串行化是不同层次的保障。
